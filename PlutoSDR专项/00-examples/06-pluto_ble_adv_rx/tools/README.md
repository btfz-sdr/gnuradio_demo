# tools/ —— 离线分析脚本（Python，需要 numpy）

这些脚本是**独立参考实现**：不共用 `ble_phy.c` 的代码，用来交叉验证 C 解调器的行为，
以及在没有 Pluto 的情况下定位问题。抓包见 makefile 的 `make capture`。

| 脚本 | 用途 |
|---|---|
| `gen_ble.py <SNR dB>` | 生成合成 BLE 广播包（LE 1M、10 Msps、交织 int16 IQ），输出 `synth_snr<N>.bin`。用于解调器回归：当前基线 **≥10 dB 出包、≤5 dB 不出**（dB 是总带内 SNR）。加噪顺序是"先归一化信号再加噪"，不要在加噪后按总峰值归一化（否则 SNR 标签非单调） |
| `aa_scan.py <阈值> <iq.bin>...` | 匹配滤波 + 全 10 相位扫 access code，输出归一化相关系数 r。**判"锅在谁身上"用**：真实信号应能到 r≈0.98（既约 40/40），若 C 解调输出落在随机统计上，问题在解调器而不在射频 |
| `decode_cand.py <iq.bin> <信道> <阈值>` | 对候选点按**候选自己的定时相位**完整解码（切片 → 解白化 → CRC-24），把真包和误报分开。输出 CRC-OK 计数，用于核对 C 的收包数是否漏包 |

## 典型用法

```bash
# 1) 从设备抓一段原始 IQ（走网络 IIO，不用登录 Pluto）
make capture CH=37 SEC=2 FILE=ch37.bin

# 2) 独立参考：有多少候选、各自相关度多高
python3 tools/aa_scan.py 0.96 ch37.bin

# 3) 独立参考：其中真正 CRC 通过的有几个
python3 tools/decode_cand.py ch37.bin 37 0.96

# 4) C 实现（同一个 ble_phy.c）跑同一段数据，对比包数
make replay FILE=ch37.bin CH=37
```

## 判据速查

- 随机比特的 AA 汉明距离均值约 **20/40**（每 257k bit 约 23 个点 ≥32/40）。
  旧版 `ble_phy.c` 基线：最高 34/40、CRC OK **0** 个 → 判决比特是纯噪声。
- 真实信号（干净包）匹配滤波后 **40/40**、软幅度约 ±1.5。
- `decode_cand.py` 的 CRC-OK 数就是"这段录波里真正能解出的包"，
  可以直接和 C 实现的收包数对比。**注意参考实现每个候选位置只试一个定时相位**，
  所以它自己也会漏包（2.1 s 录波：参考 18/18/36，C 端 18/23/47）——
  "C 明显少于参考"才是 bug 信号；"C 多于参考"是正常的。
  实测对照（修复"锁死第一个相位"之前 C 端只有 4/7/16）。
- `aa_scan.py` 的 r 与 AA 错位数大致关系：`错位数 ≈ (40 - 40r)/2`
  （r≈0.98 → 0 位错；r≈0.90 → 约 2 位错，这个量级噪声也会偶然出现，
  所以 `aa_scan` 的候选数不能当包数，必须用 `decode_cand.py` 的 CRC 结果）。

## 注意

- 这些脚本按文件名推断信道号（`ch38`/`ch39`，否则 37），抓包时文件名带上信道号更省事。
- `aa_scan.py` 第 4 个参数起是文件列表；`decode_cand.py` 只处理一个文件。
- 相关度 r 与 AA 错位数的关系是近似：`错位数 ≈ (40 - 40r)/2`，受软判决幅度影响，
  只用来快速筛，不用来下结论。
